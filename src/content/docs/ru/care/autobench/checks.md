Проверка отвечает на один вопрос: совпадает ли ответ агента со скрытым
эталоном? Метод выбирается в мастере (**Метод проверки**). Одно и то же
правило работает дважды: сначала им проверяют сгенерированные примеры, потом,
в переводе на оценщик платформы эволюции, им оценивают цепочки-кандидаты.

## Методы проверки

| Метод | Ответ верен, если | Когда брать |
| --- | --- | --- |
| **Авто** | Метод выбирает стадия спецификации из перечисленных ниже. | Не уверены. Если надёжной программной проверки нет, модель берёт судью и не натягивает шаблон на свободный текст. |
| **Судья-модель** | Решает вызов судьи по вашему критерию. | Свободный ответ: объяснения, пересказы, рассуждения. Заполните **Критерий для судьи**. |
| **Точное совпадение** | Весь ответ равен эталону (или допустимой альтернативе) после нормализации: Unicode NFKC, регистр, пунктуация в пробелы. | Короткие однозначные ответы: имя, код, дата в фиксированном формате. |
| **Метка из списка** | Ответ входит в закрытый набор меток и совпадает с эталоном. | Классификация. Укажите метки или оставьте поле пустым, тогда их предложит модель. |
| **Число** | Первое число в ответе отличается от эталона не больше чем на допуск. Пробелы и десятичная запятая не мешают. | Суммы, количества, измерения. |
| **Регулярное выражение** | Группа 1 шаблона в ответе совпадает с группой 1 в эталоне (поиск без учёта регистра). | Ответ внутри текста с маркером, например `Итого:\s*([\d.,]+)`. Перед эволюцией прочитайте оговорку [ниже](#как-проверка-становится-оценщиком-эволюции). |
| **Поле JSON** | Ответ в JSON (можно в блоке кода), и одно названное поле совпадает с полем эталона. | Структурированный вывод, где важно одно поле. Только одно поле. |
| **Содержит все части** | В ответе есть все части эталона; части разделены `\|`. | Списки обязательных пунктов в любом порядке. |

Ваш выбор важнее выбора модели. Некоторые варианты поправляются, если
спецификация их не тянет: **Метка из списка** без меток становится **Точным
совпадением**; **Поле JSON** без поля и **Регулярное выражение** без шаблона
становятся **Судьёй-моделью** (для регулярного выражения мастер требует
шаблон).

**Описание правильного ответа** всегда необязательно. При программной
проверке это подсказка для спецификации, она попадает в критерий успеха; у
**Судьи-модели** это и есть критерий.

### Допуск

Используется только допуск, который ввели вы. Допуск, который модель
придумала сама (например 0,01 для денег), отбрасывается: у ненулевого допуска
нет точного аналога на платформе эволюции. Если допуск задали вы, примеры
здесь проверяются с ним, а в эволюцию набор уходит с критерием для судьи
вместо точного совпадения. См.
[Как проверка становится оценщиком эволюции](#как-проверка-становится-оценщиком-эволюции).

## Как проверяется пример

Когда примеры пишет модель:

1. **Программные проверки.** У входа ровно поля контракта (плюс `file` для
   файлов), он не пустой, ни одно поле не длиннее 6 000 символов, нет слов
   вроде «expected», «gold», «эталон», нет обоснования ответа. Эталон входит в
   набор меток, если он задан. Пример не повторяет принятый с другими именами
   или числами. Эталон проходит собственную проверку, а заведомо неверные
   ответы (в том числе пустой) не проходят.
2. **Слепое решение.** Модель решает пример заново, не видя эталона и
   обоснования.
3. **Судья.** Отдельный вызов сверяет эталон с задачей и критерием. Для
   **Судьи-модели** он смотрит каждый пример, для программных проверок только
   те, где слепое решение не совпало.

У программы-генератора эталоны считает код, каждый пример всё равно проходит
шаг 1, а программа целиком проверяется выборкой слепых решений (см.
[Программа-генератор](/ru/care/autobench/generate/#программа-генератор)).

:::note
Слепой решатель и судья используют тех же провайдера и модель, что и
генератор. Они ловят много неверных эталонов, но общие слепые пятна
генератора не видят.
:::

## Уровни проверки

У каждого примера во вкладке **Примеры** и в происхождении версии указан
уровень.

| Уровень | Текст в приложении | Смысл |
| --- | --- | --- |
| `cross_checked` | подтверждён независимым решением | Слепое решение совпало с эталоном. |
| `judged` | решатель ошибся, судья подтвердил эталон | Слепое решение не совпало, судья подтвердил эталон. |
| `llm_judge` | проверен моделью-судьёй | Метод судьи: судья подтвердил эталон. |
| `program` | эталон вычислен программой | Посчитан программой-генератором. |
| `manual` | проверен вами | Вы написали, изменили или приняли пример. |
| `executable` | без подтверждения эталона | Проверка работает, но эталон не подтверждён. В набор не попадает. |

Итоги:

- **Принятые**: подтверждены, идут в версии.
- **Отклонённые**: не прошли проверку или судья счёл эталон неверным. Причины
  написаны у примера.
- **Без проверки**: подтвердить не удалось (решатель не ответил или судья не
  вынес решения). В набор не входят, пока вы их не примете.
- **Устаревшие**: не подходят к новой спецификации.
- **Исключённые**: убраны вами, хранятся для истории.

## Как проверка становится оценщиком эволюции

| Проверка | Оценщик эволюции |
| --- | --- |
| Точное совпадение, Метка из списка, Число с допуском 0 | `binary_match`, `equality` |
| Регулярное выражение | `binary_match`, `regexp` с вашим шаблоном |
| Поле JSON | `binary_match`, `regexp`, который достаёт это поле |
| Судья-модель, Число с допуском больше 0, Содержит все части | критерий: `LLM judge (0..1)` с выгруженным критерием |

Что нужно знать:

- При `equality` платформа сравнивает текст, а не числа: цепочка, которая
  печатает `1105.0` при эталоне `1105`, может не пройти. Зафиксируйте формат
  числа в **Формате ответа**.
- **Регулярное выражение с маркером опасно для эволюции** (по чтению кода, не
  измерялось). Здесь эталон сам должен подходить под шаблон, поэтому для
  `Итого:\s*([\d.,]+)` эталон выглядит как `Итого: 1105`. Платформа достаёт
  группу 1 из ответа цепочки (`1105`), но сравнивает её с эталоном целиком,
  и такой набор может поставить ноль любому кандидату. Пока это не
  исправлено, берите **Число** или **Точное совпадение** с фиксированным
  **Форматом ответа** либо шаблон, у которого группа 1 и есть весь эталон.
- Оценщик с критерием вызывает модель-судью на каждой выбранной строке каждой
  оценки, поэтому эволюция дороже. Ему нужна сборка платформы эволюции с
  поддержкой LLM-судьи; старая платформа отклонит запуск с
  `llm_judge_unsupported`.
- Задачи с инструментами выгружаются как `stateful_env`, в эволюцию их пока
  не отдать.
