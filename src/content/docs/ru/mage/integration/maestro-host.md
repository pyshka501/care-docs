Maestro (пакет `care`) это эталонный хост MAGE. За ним разговор,
подключение к модели, память и подтверждения; MAGE только превращает задачу в
цепочку. Генерация в Maestro никогда не запускает и не сохраняет цепочку
попутно.

## Какой MAGE запускает Maestro

С PyPI Maestro MAGE не ставит. В `pyproject.toml` (`[tool.uv.sources]`) он
закрепляет git-ревизии ветки разработки:

| Ветка Maestro | Ревизия MAGE | Что это |
| --- | --- | --- |
| `feat/maestro-library` (исходники релиза 0.5.0) | `6140b3b` (5 октября 2026) | Линия 0.2.0: типизированные запросы, допуск рантаймом, подсказки IdeaL на выбор хоста, имена цепочек по задаче. |
| `feat/dataset-studio` (разработка после 0.5.0) | `b7a6e27` (2 ноября 2026), ветка `maestro/step-field-refs` | То же плюс правки из `feat/v3-phase0`: сохранённые контракты входа переживают правку и починку, типизированные литеральные привязки, `$steps.N.tool_name`, оценка расхода, когда провайдер его не сообщает, и правка экспорта (поле результата шага это `$steps.N.result_data.<field>`, а не `$history[N].<field>`). |

Обе сообщают версию `0.2.0+ideal.20261005.1`. Обе запускают `MAGEGenerator`
со стратегией `legacy`, она в этих ревизиях по умолчанию.
[Стратегии `v3`](/ru/mage/concepts/v3-generator/) нет ни в одной из них: она
есть только в кандидате 0.2.0 (`prep/mage-0.2.0`), который Maestro не
закрепляет, так что Maestro v3 **не использует**. Цикла памяти и кузниц тоже
нет ни в одной ревизии. На ветке разработки десктопного приложения цепочки
по умолчанию пишет сам чат-агент, и MAGE вообще не вызывается, пока вы о нём
не попросите (см. ниже).

:::caution[Переход Maestro на MAGE 0.2.0 переключит его на v3]
Maestro собирает `MAGEConfig` без `generation_strategy` (`care/generation.py`
на `feat/dataset-studio`). С закреплёнными ревизиями это значит `legacy`, с
0.2.0 уже `v3`. Если Maestro не задаст `generation_strategy="legacy"` в коде
или полем секции `[mage]` (оно передаётся дальше, потому что MAGE его
объявляет), генерация изменится:

- `mode`, переключатели стадий deep и поиска из `[mage]` перестанут
  действовать.
- Доступны будут только инструменты из `capabilities`, которые передаёт
  Maestro.
- Задача, у которой в схеме входа есть приватное поле, не пройдёт допуск:
  v3 там отклоняет любой шаг `llm`.
- Найденный контекст и подсказки IdeaL, которые передаёт Maestro, промпты
  v3.4 не читают.
- Каждая генерация стоит больше вызовов модели (план, автор, починки, сухой
  прогон).
- Список шагов для развёртывания (`allowed_step_types` без `human_input`)
  проверяется при допуске.

Это прочитано по коду; Maestro на 0.2.0 не запускали.
:::

В зависимостях Maestro по-прежнему написано `mmar-mage>=0.1.4`, а такая
версия не выходила. Поэтому Maestro ставится только из клона, где действуют
git-пины. Пин CARL из самого MAGE Maestro тоже заменяет своей ревизией CARL.

## Когда Maestro зовёт MAGE

- **CLI и TUI:** `maestro generate` и экран генерации в TUI всегда используют
  MAGE с настройками `[mage]` (`CARE_MAGE__*`): эндпоинт, модель, ключ,
  режим, переключатели поиска. См.
  [Генерация, запуск и повтор](/ru/care/cli/generate-run/).
- **Приложение, 0.5.0:** харнесс Maestro выбирает стратегию под каждый
  запрос о цепочке. Новая цепочка обычно идёт через `generate_chain`, то есть
  через MAGE и инструмент `maestro_generate_chain` (или фоновую задачу).
  `author_chain`, когда чат-агент пишет CARL сам, включается по вашей
  просьбе.
- **Приложение, ветка разработки:** по умолчанию наоборот. Настройка
  `defaults.chain_author` (`CARE_DEFAULTS__CHAIN_AUTHOR`) равна `agent`:
  чат-агент смотрит реальные ответы API, пишет цепочку, проверяет её и
  прогоняет на примере. С `mage` или если вы явно просите MAGE, генерация
  идёт через MAGE как раньше. Не выпущено.

## С какой моделью говорит MAGE

MAGE сам создаёт OpenAI-совместимый клиент из `MAGEConfig`. Maestro всегда
ставит `provider="custom"` и заполняет `base_url`, `api_key`, `model`:

- **CLI и TUI:** из `[mage]`.
- **Приложение:** из чат-сессии, которая попросила цепочку, через приватный
  мост к модели чата в харнессе. MAGE получает loopback-адрес и
  короткоживущий ключ прокси; ключ провайдера остаётся в харнессе. Если у
  операции с цепочкой нет привязки к чату, она падает, а не берёт ключ из
  `[mage]`. Мост поднимает HTTP-таймаут MAGE до 300 с (не больше
  `max_wall_time_seconds`), потому что прокси отдаёт ответ целиком. На ветке
  разработки `defaults.chain_model = "custom"` направляет операции с
  цепочками на эндпоинт `[mage]`.

## Что Maestro передаёт

`care/generation.py` собирает `MAGEConfig` и `GenerationRequest`:

| Вход | Как заполняет Maestro |
| --- | --- |
| `MAGEConfig` | Каждое поле `[mage]`, которое объявляет установленный MAGE (неизвестное поле это ошибка, а не молчаливый пропуск); `mode`; `provider="custom"`; `memory_base_url` = адрес памяти Maestro. |
| Переключатели памяти | Если память цепочек это IdeaL: `enable_memory`, `enable_memory_research`, `enable_memory_skill_lookup` выключены, потому что ищет сам Maestro. |
| Цепочки для развёртывания | `allowed_step_types` без `human_input`: развёрнутому агенту некому отвечать. |
| `current_task` | Безопасная задача, без тел файлов и приватных путей. |
| `project_instructions` | Постоянные инструкции пользователя и проекта. |
| Файлы | По записи `input_manifest` на файл (имя, вид, тип, размер, хеш, профиль) и тело как приватный `retrieved_untrusted_context`. |
| Контекст хода | Текст продолжения разговора, если он богаче задачи, без вложений, как приватный недоверенный контекст. |
| Найденный контекст | То, что Maestro нашёл о похожих цепочках, как недоверенный контекст (`gigaevo-recall` или `ideal-catalog`). Для IdeaL включается выборочный режим, чтобы модель видела только этот элемент. |
| `runtime_input_schema` | Контракт входа цепочки, если он есть в плане. |
| Политики | `external_research="safe_task_only"`, `PersistencePolicy(mode="explicit_only")`: MAGE ничего не сохраняет. |
| `capabilities` | Каталог инструментов Maestro как закрытый `CapabilityContext`. |
| `cancel`, `progress` | Esc или кнопка отмены задачи; прогресс показывается в интерфейсе. |

Что каждое поле значит для MAGE, см. в
[Типизированных запросах и допуске](/ru/mage/concepts/typed-authoring/).

## Что Maestro проверяет на обратном пути

Собственной проверке MAGE Maestro последнее слово не оставляет:

1. Цепочка достаётся из результата, схема входа прикрепляется к её
   метаданным.
2. Детерминированная проверка запросов инструмента веб-поиска, с одной
   починкой без вызова провайдера.
3. Ещё раз `validate_runtime_chain()`, со схемой входа, на том CARL, который
   запускает Maestro.
4. Только после этого цепочка кладётся приватным артефактом, закреплённым по
   SHA-256, с карточкой структуры и сводкой готовности. Сохранение, запуск,
   развёртывание и эволюция это отдельные действия со своими квитанциями и
   подтверждениями.

Ошибки приходят в чат типизированными кодами (`provider_failed`,
`generation_validation_failed`, `invalid_generation_result`,
`chain_admission_failed`) с диагностикой, а не сырым ответом провайдера.
