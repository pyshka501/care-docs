`MemoryStepDescription` выполняет одну операцию над хранилищем памяти контекста,
разбитым на пространства имён. Через него удобно сохранять промежуточные
результаты, которые потом читают другие шаги. Вызова LLM нет.

## MemoryStepConfig

| Поле | Тип | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `operation` | `MemoryOperation` | (обязательное) | `read` / `write` / `append` / `delete` / `list`. |
| `memory_key` | `str` | (обязательное) | Ключ в хранилище памяти. Нужен и для `list`, хотя там не используется. |
| `value_source` | `str \| None` | `None` | Откуда берётся значение для `write` / `append`, например `"$history[-1]"`. |
| `default_value` | `Any` | `None` | Для `read`: возвращается, если ключа нет. Для `write` / `append` без `value_source`: записываемое значение. |
| `namespace` | `str` | `"default"` | Пространство имён для изоляции. |

Память устроена как **пространство имён → ключ**. В других местах её читают
[ссылкой](/ru/carl/chains/dynamic-references/) `$memory.namespace.key`
(`$memory.key` читает из пространства `default`).

Что делает и возвращает каждая операция:

| Операция | Действие | `result_data` |
| --- | --- | --- |
| `read` | Читает ключ или `default_value`. | Значение. |
| `write` | Перезаписывает ключ. | `{"key", "namespace", "value"}` |
| `append` | Дописывает в список, при необходимости сначала создаёт `[]`. Падает, если по ключу лежит не список. | `{"key", "namespace", "appended"}` |
| `delete` | Удаляет ключ, если он есть. Отсутствие ключа не ошибка. | `{"key", "namespace", "existed"}` |
| `list` | Перечисляет ключи пространства имён. | `list[str]` |

`value_source` разрешается как ссылка. Значение, которое не начинается с `$` и
не разрешается, записывается как строковый литерал.

Если у цепочки или контекста есть [схема памяти](/ru/carl/memory/schema/), `write`
и `append` сначала проходят проверку типов. При несовпадении шаг падает, и ничего
не записывается.

## Пример: запись, затем чтение

```python
from mmar_carl import MemoryStepDescription, MemoryStepConfig, MemoryOperation

# Step 3 stores step 2's output under results/analysis
MemoryStepDescription(
    number=3,
    title="Store result",
    dependencies=[2],
    config=MemoryStepConfig(
        operation=MemoryOperation.WRITE,
        memory_key="analysis",
        value_source="$history[-1]",
        namespace="results",
    ),
)

# A later step reads it back
MemoryStepDescription(
    number=5,
    title="Retrieve result",
    dependencies=[3],
    config=MemoryStepConfig(
        operation=MemoryOperation.READ,
        memory_key="analysis",
        namespace="results",
        default_value="(missing)",
    ),
)
```

`$history[-1]` это полная запись истории предыдущего шага (`Step N. Title` плюс
`Result: ...`). Чтобы сохранить только значение результата, используйте
`$metadata.step_N`. Там лежит `result_data` этого шага (или `result`, если
структурированных данных нет).

## Память при параллельном выполнении

Шаги одного параллельного батча работают с copy-on-write представлениями памяти.
Правила такие:

- **Соседи не видят записей друг друга.** Каждый шаг батча видит память такой,
  какой она была до батча. Записи становятся видны следующим батчам.
- **Чтение не откатывает записи.** Обратно сливаются только ключи, которые шаг
  действительно записал или удалил. Шаг, который только читает пространство имён,
  ничего не вносит в слияние (но см. предупреждение ниже про списки и словари).
- **Вложенные значения изолированы.** При чтении изменяемого значения (списка,
  словаря) шаг получает свою копию. Изменения на месте, например `append`,
  обнаруживаются и сливаются как записи. Напрямую к родителю или соседу они не
  попадают.
- **Конфликт по одному ключу решает последняя запись в порядке объявления
  шагов.** Если два шага одного батча пишут (или пишут и удаляют) один ключ,
  побеждает шаг с бо́льшим номером, независимо от того, кто закончил раньше.
  Это верно при любом `max_workers`.
- **Дописывание это запись всего списка, а не объединение.** Если два шага в
  одном батче дописывают в один список, остаётся список шага с бо́льшим номером,
  а другое дописывание теряется. Если нужны оба, разнесите такие шаги по разным
  батчам (добавьте зависимость).
- **Слитые значения проходят схему памяти.** Значение, нарушающее схему памяти,
  не сливается, а записавший его шаг помечается упавшим.

:::caution[Известная проблема: значения-списки и словари]
Если один шаг батча пишет или дописывает в ключ со **списком или словарём**, а
шаг того же батча с бо́льшим номером этот ключ только читает, после слияния может
вернуться старое значение. Изолированная копия читателя сравнивается с родительским
значением уже после слияния записи. Поэтому она выглядит как изменение и сливается
последней. Скалярные значения (строки, числа, булевы) не затронуты. Пока это не
исправлено, не читайте и не пишите один и тот же ключ со списком или словарём в
одном параллельном батче: сделайте читателя зависимым от писателя.
:::

Подробности и обоснование правил: [copy-on-write память](/ru/carl/memory/cow/).
